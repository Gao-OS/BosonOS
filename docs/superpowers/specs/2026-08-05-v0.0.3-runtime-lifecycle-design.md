# BosonOS v0.0.3 Runtime Lifecycle Design

## Status

Design and implementation plan approved; amended after pre-implementation
review.

## Goal

BosonOS v0.0.3 proves that the BEAM runtime owns the system lifecycle, not
only that an OTP release can start. The milestone adds trustworthy runtime
readiness, component health tracking, and a one-shot BEAM-to-Gluon machine
action protocol.

The boot chain remains:

```text
Linux -> Gluon PID 1 -> Boson OTP release -> Boson supervision tree
```

Gluon remains a minimal launcher and policy executor. It does not learn about
OTP components or become a service manager.

## Existing Baseline

The v0.0.2 x86_64 and AArch64 QEMU images boot through Gluon into the Boson
release. The current smoke test accepts `Boson.Boot online`, but that message is
emitted by the first supervisor child before the remaining runtime components
have started. Bus, Device, Net, Console, and Update are supervised stubs and do
not currently participate in a readiness contract.

Gluon already waits for the release process and applies `on_exit` or
`on_crash`. There is no way for the BEAM runtime to request a specific machine
action.

## Scope

The milestone includes:

- A runtime lifecycle coordinator in `Boson.Boot`.
- Component readiness registration and process monitoring.
- A stable `Boson.Boot.status/0` API.
- A one-shot `/run/boson/action` protocol.
- Gluon action parsing, consumption, and policy selection.
- Real runtime tests in the Nix package check phase.
- Normal-boot and lifecycle-action QEMU checks on x86_64 and AArch64.
- Updated architecture, boot, init-contract, build, and release documentation.

The milestone excludes:

- Persistent `/data` storage.
- OTA or image update behavior.
- Real device enumeration or network management.
- RK3566 kernel, bootloader, image, or hardware boot work.
- An external control API, Unix socket, or interactive console command channel.
- Additional Gluon-managed services or dependency graphs.

## Runtime Architecture

### Supervision Tree

`Boson.Supervisor` remains a `:one_for_one` supervisor. It owns the single
ordered list of required runtime component modules:

```text
Boson.Boot
Boson.Bus
Boson.Device
Boson.Net
Boson.Console
Boson.Update
```

The supervisor passes the component list, excluding `Boson.Boot`, to the Boot
child. This prevents separate supervision and readiness lists from drifting.

Every component is registered under its module name. A component reports
readiness only from `handle_continue/2`, after its own initialization has
completed:

```elixir
Boson.Boot.component_ready(__MODULE__, self())
```

Boot accepts that report only when the GenServer caller PID, the reported PID,
and the component's registered PID are identical. Each component also handles a
private `:boson_readiness` call and replies with
`{:ready, component_module, self()}`. That call is used only to re-establish
readiness after a Boot restart; a GenServer cannot answer it until `init/1` has
completed.

The component decides when it is ready. `Boson.Boot` does not inspect component
internals or impose a dependency graph.

### Lifecycle Coordinator

`Boson.Boot` becomes a named GenServer with these public functions:

```elixir
Boson.Boot.status()
Boson.Boot.component_ready(component, pid)
Boson.Boot.request_action(:reboot | :poweroff)
```

Its status has a stable shape:

```elixir
%{
  phase: :starting | :ready | :stopping,
  started_at_ms: integer(),
  ready_at_ms: integer() | nil,
  online_components: [module()],
  missing_components: [module()],
  last_action: :reboot | :poweroff | nil
}
```

Component lists are sorted to keep status and tests deterministic.

The application creates a lifecycle context when it starts and stores it in
`:persistent_term`. The context contains a unique boot reference, the runtime
start time, the first ready time, and whether the initial ready marker was
emitted. Boot updates this metadata only on the first ready transition. The
context therefore survives a Boot-process restart without adding another
long-lived process and is reset when the Boson application starts a new boot
epoch.

### Readiness Transitions

The lifecycle begins in `:starting`.

- A valid readiness report records the component PID and installs a monitor.
- Duplicate reports for the same component and PID are idempotent.
- A new PID for the same component replaces the old PID and monitor.
- A report from a module outside the required set is rejected and logged.
- The transition to `:ready` occurs only when every required component is
  online.
- The first transition emits exactly one `Boson.Runtime ready` marker for the
  runtime boot epoch.

When a monitored component exits, Boot removes it and returns a ready runtime to
`:starting`. It logs the unavailable component and exposes it through
`missing_components`. The OTP supervisor restarts the component. A later valid
readiness report can restore `:ready`; this emits `Boson.Runtime recovered`
rather than another initial ready marker. A runtime already in `:stopping`
preserves that phase and its selected action during component shutdown churn.

Monitor messages are matched against the currently recorded PID and reference.
A delayed `:DOWN` message from a replaced PID cannot remove its replacement.

If `Boson.Boot` itself restarts, it looks up each required registered process
and starts an independent bounded worker for the private `:boson_readiness`
GenServer call. Boot does not make that call from its own callback, so it remains
able to accept a component's synchronous readiness report while a probe is in
flight. Each result carries a private reference recorded in Boot's state. Boot
records and monitors a component only when the reference and candidate match,
the reply contains the expected module and PID, and the name still resolves to
that PID. Results received after Boot enters `:stopping` are ignored. A
registered PID alone is never readiness proof because OTP registers a named
GenServer before its `init/1` callback completes. Missing, initializing,
non-responsive, or mismatched components remain missing until a valid probe or
readiness report succeeds. This permits `:one_for_one` supervision to remain in
place without restoring the premature-readiness bug or creating a cyclic
GenServer call between Boot and a component.

## Machine Action Protocol

### BEAM Writer

`Boson.SystemAction` is a pure functional module, not a supervised process. It
writes one of two exact payloads:

```text
reboot\n
poweroff\n
```

The production path is fixed:

```text
/run/boson/action
```

The writer ensures `/run/boson` exists, creates a uniquely named temporary file
there, writes and syncs the payload, applies mode `0600`, and atomically renames
the file to `action`. Tests may pass a temporary path directly to the writer;
the target runtime does not gain another configuration key.

`Boson.Boot.request_action/1` accepts requests only in `:ready`:

- An unsupported value returns `{:error, :unsupported_action}`.
- A request while starting returns `{:error, :not_ready}`.
- A request while stopping returns `{:error, :already_stopping}`.
- A write failure returns the concrete error and leaves the phase at `:ready`.
- A successful write records the action, enters `:stopping`, replies `:ok`, and
  asynchronously invokes `System.stop(0)`.

The shutdown function is injected in Boot tests. Production always uses
`System.stop(0)`.

If Boot restarts after a valid action was written, it detects the pending file,
restores `:stopping`, and resumes the clean shutdown. A malformed pending file
causes a non-zero runtime stop so Gluon applies crash policy.

### Gluon Consumer

Gluon removes any stale action file after mounting `/run` and before launching
the OTP release. A cleanup failure other than a missing file is fatal to the
runtime launch, because Gluon cannot safely distinguish a later action from a
stale one.

After the runtime process exits, Gluon selects behavior in this order:

| Runtime result | Action file | Result |
| --- | --- | --- |
| Non-zero or signaled | Any | Remove action if possible; apply `on_crash` |
| Zero | Missing | Apply `on_exit` |
| Zero | Valid `reboot` | Remove file; reboot |
| Zero | Valid `poweroff` | Remove file; power off |
| Zero | Invalid, unreadable, or too large | Remove if possible; apply `on_crash` |
| Zero | Valid but removal fails | Apply `on_crash` without executing the action |

Crash status always wins over a pending action. Gluon reads only a small bounded
payload and accepts no arguments, extra tokens, service names, or arbitrary
commands.

The consumer logs a stable marker before applying a valid request:

```text
gluon info: applying runtime action: poweroff
```

The existing `reboot`, `poweroff`, `hang`, and `emergency_shell` exit-policy
implementation remains the final machine-operation mechanism.

## Failure Semantics

- A required component that fails initialization never contributes readiness.
- If supervisor restart intensity is exceeded, the release exits non-zero and
  Gluon applies `on_crash`.
- A component crash after ready immediately invalidates readiness, while OTP
  remains responsible for restarting it.
- Action-file failure does not stop a healthy runtime.
- A runtime crash after writing an action cannot turn into a requested reboot or
  poweroff; the non-zero exit selects `on_crash`.
- During `:stopping`, component shutdown churn does not change the selected
  action or admit a second request.
- Gluon action read, validation, and removal errors are explicit and bounded;
  none fall back to executing untrusted content.

## Testing Strategy

### Elixir Tests

ExUnit covers:

- Initial and recovered readiness transitions.
- Deterministic status contents.
- Duplicate readiness reports and PID replacement.
- Stale monitor-message handling.
- Component loss and re-registration.
- Boot restart reconciliation.
- A named component that is registered but still inside `init/1` remaining
  unready until it answers the explicit readiness probe.
- Unsupported, premature, and duplicate action requests.
- Atomic action payload, mode, and write failure behavior.
- Pending-action recovery.
- The real Boson supervisor reaching ready.
- A required child startup failure never producing ready.

`nix/packages/runtime.nix` enables `doCheck` and runs `mix test` in a check
phase before the release derivation succeeds. The existing `runtime-build`
check continues to point at that derivation, so it now proves both tests and
release construction.

### Zig Tests

Gluon tests separate parsing and policy selection from privileged machine
operations. They cover:

- Both valid action payloads.
- Missing, empty, unknown, extra-token, and oversized payloads.
- Read and removal failures.
- The full exit-status and action-result decision matrix.
- Crash precedence over valid actions.
- Startup stale-file cleanup behavior.

The filesystem reader/remover is behind an internal generic operations seam.
Production uses absolute-path file operations; tests inject deterministic read
and removal results. This proves that the consumer classifies operation
failures as `read_error` or `remove_error`, and that startup cleanup failure is
terminal, without permission-sensitive tests.

No Zig unit test invokes reboot or poweroff.

### QEMU Checks

`qemu-boot-smoke` waits for `gluon info: starting` and
`Boson.Runtime ready`. It then observes a ten-second stability window. The guest
must remain alive and the console must not contain runtime-unavailable, crash,
or kernel-panic markers.

A new `qemu-lifecycle-smoke` uses a test-only runtime and rootfs derivation.
`nix/packages/runtime.nix` accepts an internal `lifecycleTestAction ? null`
argument. The normal flake package uses `null`; the lifecycle check calls the
package with `"poweroff"` and builds a private runtime, rootfs, image, and QEMU
app graph. That build-time application setting requests poweroff after first
reaching ready. The private derivations are used only by the check and are not
exposed as packages or release assets. The check requires, in order:

```text
Boson.Runtime ready
Boson.Runtime stopping action=poweroff
gluon info: applying runtime action: poweroff
```

QEMU must then exit normally. Unit tests cover the parallel reboot branch, so
the expensive lifecycle boot check runs once per architecture rather than once
per action.

Both x86_64 and AArch64 native CI jobs build the image, run normal boot smoke,
and run lifecycle smoke. The source-test workflow runs on every pushed branch,
so the feature branch can satisfy both the `Test` and `CI` gates before merge.

## Release And Documentation

The split release workflows remain unchanged in purpose:

- `Release` creates the release page.
- `Build Release Image` builds and uploads a selected device artifact.
- `E2E` downloads and boots a released artifact.

Released-artifact E2E changes its success marker to `Boson.Runtime ready` and
uses the same stability window. Release images do not automatically request a
machine action.

After the implementation is merged and `main` CI passes, the verified merge
commit SHA is passed to the release workflow as `git_ref`; the mutable `main`
name is not used as the tag target. The existing manual workflows then publish
v0.0.3, upload both QEMU images and checksum files, and run released-artifact
E2E for both device IDs. Publication happens only after the source-level
dual-architecture checks pass, and the release tag must resolve to that verified
commit before any asset is uploaded.

The documentation set for this milestone is:

- `README.md`
- `docs/BOOT.md`
- `docs/GLUON.md`
- `docs/INIT_CONTRACT.md`
- `docs/SYSTEM_MODEL.md`
- `docs/NIX_BUILD.md`
- `.github/release-notes.md`

Documentation must continue to state that `/data`, OTA, real device services,
and RK3566 hardware boot are outside this milestone.

## Acceptance Criteria

1. `Boson.Boot.status/0` reports the approved stable status shape.
2. The initial ready marker appears only after every required component reports
   ready.
3. Component loss removes readiness and OTP restart restores it.
4. BEAM can request reboot or poweroff only through a valid atomic action file.
5. Runtime crash status takes precedence over every action-file state.
6. Gluon never executes unknown action content and remains free of service
   supervision logic.
7. The runtime Nix derivation runs ExUnit before producing a release.
8. Normal boot smoke observes ten stable seconds after readiness on x86_64 and
   AArch64.
9. Lifecycle smoke reaches ready, requests poweroff, and exits QEMU normally on
   both architectures.
10. v0.0.3 publishes x86_64 and AArch64 QEMU assets with checksum files.
11. Released-artifact E2E boots both assets using the trustworthy ready marker
    and the ten-second stability window.
